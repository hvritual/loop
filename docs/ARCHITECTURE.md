# 架构与取舍

## 权威来源

| 问题 | 唯一权威 |
|---|---|
| 为什么做、目标和范围 | intent.json 与真实用户决策来源 |
| 系统应如何表现 | spec.json |
| 方案与交互如何实现 | design.json 引用的设计快照 |
| 当前做哪一步、完成了什么任务 | 原生 GSD STATE / ROADMAP / PLAN / SUMMARY |
| 实现和外部系统实际发生什么 | Git、命令执行日志、PR/CI、部署/运行回执 |
| 允许怎样做 | 版本化 Rules；外部权限/保护机制负责硬约束 |

plan-map.json 仅投影原生 GSD 计划与验收的映射，禁止存任务 status。checkpoint.json 仅用于恢复索引；它过期时必须对账，不覆盖真实状态。

## 不建设的东西

没有自研模型客户端、任务调度器、状态数据库、后台守护服务、分布式锁或自行假设的 exactly-once 保证。不同模型共享文件契约与技能；原生格式适配由 GSD/BMAD 官方安装器完成。

脚本采用 Python 标准库，不依赖 LLM 进行机械检查。检查通过不自动调度下一阶段，也不自动批准、合并或部署。

## BMAD 的边界

只公开经过 allowlist 的研究、规格、UX、架构、审阅及项目上下文技能。安装后将 BMAD 的自动 build、sprint、ship 等非允许原生入口移出发现目录，保存于 `.loop-cache/disabled-bmad/`。原始上游定义不被改写。

这降低误调用风险，但不构成对拥有文件访问权限模型的安全隔离。BMAD 分析报告可保留在 `_bmad-output/`，正式采纳的结论必须引用/转入 intent/spec/design，并进入版本管理；该输出目录不是进度数据库。

## 哈希失效链

用户决策快照 → Intent 内容摘要 → Spec 的 intent_sha256 → Design 的 spec_sha256 → Plan Map 的 spec/design/PLAN 哈希 → Evidence Index 的 spec 哈希 → 当前源码/规则/测试摘要。

反馈先定位属于目标、行为、设计还是实现，再修改所属产物。只重做受影响检查；不以旧摘要覆盖新用户决策。

## 可信边界

本地文件可被同一权限主体修改，审批/评审字段不能认证人的身份。语义评审、真正的权限控制与不可绕过的合并规则必须来自独立人员/受保护 CI/GitHub 设置。

不确定的网络响应尤其不能作为失败重试：先查看外部状态。只有真实回执确认不存在重复效果时才能继续。
